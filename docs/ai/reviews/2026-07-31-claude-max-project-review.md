## 1. 总体判断

设计质量在这一类项目里属于中上，可靠性内核的选择是对的。真正的问题是投入比例：4 个提交里 3 个是元工作（`Add AI development workflow`、`Add Claude second-brain MCP`、`Enable fast model routing`），7 份治理文档在管 0 行产品代码，而仓库已经不满足自己定的阶段 0 验收（方案 1896 行 `dotnet build` 必须通过；`CLAUDE.md:7`、`STATUS.md:12` 确认解决方案不存在）。

更值得警惕的是：立项理由（`CLAUDE.md:58`）目前只是四句口号，不是可实现的状态机。下面第 3 节列的缺口——游标推进规则、冷启动通知、并发幂等写入、sync 分页——全部是规格缺口而非代码缺口。这些留给每个任务临场发挥，就是这个项目最可能失败的方式。

## 2. 最强的设计决策

- **发送走 HTTP、幂等键由客户端生成、提交事务后才推送**（方案 4.2:283-302、12.1:1196-1210、`DEC-002`）。关键不是"先入库后推送"这句话，而是把幂等性放在 HTTP 层：重试安全性因此不依赖连接状态，而连接状态恰恰是聊天应用真正会坏的东西。
- **单一入库函数 + source 枚举**（方案 12.5:1256-1264）。规格里写下"不要写两套插入逻辑"比那个函数签名更有价值，这是重复消息 bug 的第一来源。
- **显式的架构否决清单**（方案 6.2:465-483、2.2:151-176）。对 AI 驱动的开发来说，"不许引入 Redis/MQ/ES/CQRS/DDD"这类负向约束比任何正向需求更承重。
- **诚实的"尚不存在"标记**（`CLAUDE.md:9,39`、`AGENTS.md:27`、`WORKFLOW.md:52` 禁止"总是成功"的占位脚本），并且任务记录第 86 行真的把 `dotnet build` 标成了 `未验证`。这条纪律至少被执行过一次，有证据。

## 3. 风险、矛盾与遗漏

1. **`LastSyncedMessageId` 的推进规则完全没写，这是最危险的一处**（`CLAUDE.md:69`、方案 12.4:1244-1252）。如果实时推送也推进这个游标：短暂断线漏了消息 50，重连后先通过 Realtime 收到 51 并把游标推到 51，那条 50 就永久丢失。唯一安全的规则是"只有 Sync 来源、且连续无空洞时才推进游标"，这句话必须落到规格里。
2. **`ProcessIncomingMessage(message, source)` 的 source 有参数没语义**（方案 1263-1273）。四种来源在"是否推进游标 / 是否通知 / 是否算未读 / 是否更新会话预览"上的行为矩阵没有任何一处定义。History 尤其必须既不通知也不推进游标。
3. **冷启动通知风暴**（方案 13.1:1307-1320 + 13.2:1330）。客户端整夜关闭后重启，200 条漏消息 `IsNotified` 全是 false，13.1 的条件全部满足，会逐条弹 Windows 通知。`CLAUDE.md:71` 的 `LastNotifiedMessageId` 大概就是为了解决这个，但它的作用、与 `IsNotified` 的优先级、批量场景的聚合策略都没写，而且它在我看到的方案 13.x 里根本不存在——这与 `CLAUDE.md:43` 宣称方案是"唯一真源"直接冲突。
4. **幂等实现是先查后插，抗不住并发**（方案 12.1:1202-1203）。最常见的真实场景是客户端超时重试而首个请求仍在飞行中，两个请求都通过检查，一个撞 UNIQUE 约束，而流程里没有"捕获唯一键冲突 → 回读并返回已有记录"这一支。必须改成先插入后捕获冲突。同时未定义：幂等重放返回 200 还是 201（影响客户端 Sending→Sent 状态机）、重放是否再次推送 `NewMessage`（应明确不推）、`ClientMessageId` 的格式与长度校验（客户端可控的唯一键是滥用面）。
5. **`/api/sync` 没有分页契约**（方案 1247-1250 "返回所有新消息"）。缺 `limit`/`hasMore`/`nextCursor`。离线一周的用户会拿到一个巨大响应，而这条路径正是断线恢复要走的。
6. **只在重连时补拉，补不上推送失败**（方案 12.4:1244、`CLAUDE.md:69`）。提交事务之后推送失败或进程崩溃，消息已入库但无人知晓；连接一直不断的话，这条消息要等到下次重连才可见。建议同一个游标拉取额外挂到低频定时器（60 秒）和窗口激活事件上，复用同一入库路径，成本极低。
7. **游标是全局的，可见性是按会话且可变的**（方案 1250、`CLAUDE.md:69`）。用户被加入一个已存在的私有频道后，`MessageId` 小于当前游标的历史消息永远不会被 sync 拉到。需要明确这部分由 History 加载负责，还是 sync 需要按会话记录游标。
8. **`假设`：sync 正确性依赖 SQLite 单写者串行化**。如果 `MessageId` 是自增整数，并发事务可能出现 ID 100 提交晚于 101，sync 返回 101 后游标推进，100 永久漏掉。SQLite 单写者基本规避了这一点，但这意味着"以后换 Postgres 或开多写连接"会静默破坏补拉。这条约束应该写进 `DECISIONS.md`。表结构我没看到，`MessageId` 若不是单调整数，整个游标方案不成立。
9. **中文部分匹配的实现机制悬空**（方案 2.1:126-127 要求中文部分匹配和附件名搜索，2.2:164 禁用 Elasticsearch）。FTS5 默认分词器不切中文。对 20 人团队来说 `LIKE '%kw%'` 完全够用多年，但这必须是一条显式决策并写明行数上限，否则将来有人会用 Elasticsearch 来"修复"它，直接撞上 2.2:164。同时全局搜索必须服务端按 `ConversationMembers` 过滤（`CLAUDE.md:75`），FTS 方案下过滤要加在命中之后。
10. **附件没有大小上限、磁盘配额和清理策略，也没有备份路径**（方案 2.1:113 视频当普通文件发、3.4:225 存 VPS 本地目录）。方案 2.2:176 推迟的是"自动备份恢复界面"，这没问题；但我看到的 24.1-24.3（2527-2559 行）里也没有任何对备份机制的要求。全团队沟通记录躺在单个 SQLite 文件加一个本地目录里，这是这套部署最可能在第二个月死掉的地方。
11. **文档重复导致的漂移风险**。"没有解决方案"这一事实写在 4 处（`CLAUDE.md:7`、`AGENTS.md:14`、`README.md:30-31`、`STATUS.md:12`），"`verify.ps1` 不存在"写在 3 处（`CLAUDE.md:39`、`AGENTS.md:27`、`WORKFLOW.md:52`）。脚手架落地那一刻这些必须原子更新，否则仓库开始对自己的 agent 说谎。
12. **`STATUS.md:10` 这个字段是空信息**。"最近验证通过的状态：本文件所在提交"自指，文件无法记录自己的哈希；而读取时跑 `git log -1` 拿到的是 HEAD，不是最后验证通过的提交。偏偏 `WORKFLOW.md:104` 要求"新任务从状态页恢复，不依赖历史聊天"，唯一的锚点字段却是空的。任务文件第 6 行的写法（记录基准提交 `514f12c...`）才是对的。
13. **`DECISIONS.md` 在执行循环里没有触发点**。`WORKFLOW.md:68-71` 的"记录与提交"只要求更新任务日志和 `STATUS.md`，从未提到 `DECISIONS.md`。按 `DECISIONS.md:3` 的范围，协议和数据库决策必须入册，但没有任何环节强制这件事，这个决策日志会在第一个真实取舍出现时就开始过期。
14. **`假设`：Windows 通知激活链路是第一版技术风险最高的一项，而且被排在后面**（`README:103` 在 `README:102` 之后）。方案 13.4:1356-1364 要求点击通知激活窗口并跳到对应消息，方案 24.2:2549 把它列为交付标准。非打包 WPF 应用使用 Windows App Notifications 需要 Windows App SDK 引导和 AUMID/COM 激活器注册，这与安装包和"下载完整安装包后重启"的更新流程（方案 3.5:230-238）是耦合的。等到后期才发现注册要求，可能反过来推翻已定的更新机制。这条是基于平台常识，不是仓库证据。

## 6. 下一步三件事（按优先级）

### 优先级 1：落地阶段 0 脚手架，但要收窄

`RelayCove.sln` 加四个项目、`global.json`（SDK `10.0.101`）、`.editorconfig`、共享构建配置，以及一个真的 `scripts/verify.ps1 -Mode Fast|Full`。GitHub Actions 放在本地 `Full` 跑通之后，不要和脚手架捆在同一个切片里。顺手把 `CLAUDE.md` 提交，把 `STATUS.md:10` 改成记录上一个任务的基准哈希。

验收标准里必须加一条现在没人写下来的：**故意破坏一次代码和一次格式，确认 `verify.ps1 -Mode Full` 真的失败**。否则你造出来的正是 `CLAUDE.md:9` 和 `WORKFLOW.md:52` 明令禁止的"总是成功"的脚本，而且没人会发现。

理由：在这之前，整套工作流的 Fast/Full 验证、证据规则、`已验证` 标注全部无法执行——没有东西可跑。

### 优先级 2：把消息、同步、通知契约写成规格补充，并新增 `DEC-003`

内容就是第 3 节的 1-8 项：游标推进规则（仅 Sync 且连续）、四种 source 的行为矩阵、幂等 POST 改为先插入后捕获冲突并定义状态码与"重放不再推送"、sync 的 `limit`/`hasMore`/`nextCursor`、除重连外增加定时与窗口激活拉取、冷启动通知抑制与 `IsNotified`/`LastNotifiedMessageId` 的优先级、后加入会话的历史补齐归属、单写者依赖。

理由：这些是规格问题不是代码问题，现在写要几小时，留到实现阶段调试要几周。而且 `WORKFLOW.md:86-95` 要求对同步和通知做独立复核——契约不明确，复核无从下手。涉及协议与数据库，按 `DECISIONS.md:3` 必须入册；顺便把 `DECISIONS.md` 的更新加进 `WORKFLOW.md:68-71` 的记录环节。

### 优先级 3：做一个限时的通知激活探针

在刚建好的 Client 项目里验证：弹出 Windows 通知 → 点击 → 激活主窗口 → 携带 `conversationId + messageId` 跳到对应会话（方案 13.4:1356-1364）。明确要回答的是：非打包 WPF 需要哪些 Windows App SDK 引导和 AUMID 注册步骤，以及这些步骤必须由安装包完成到什么程度。

理由：这是第一版里唯一一项可行性取决于平台行为、无法靠设计绕开的需求，它直接卡住方案 24.2:2549。更要紧的是它和更新机制耦合：如果通知激活对应用身份或安装期注册有硬要求，方案 3.5:230-238 那套"下载完整安装包、启动安装器、装完重启"的流程可能要重做。这件事晚发现的代价不是多写一点代码，而是推翻一个已定的决策。探针代码用完即弃，结论写进任务记录。
