## 二、被新证据坐实并加强的结论

**幂等的先查后插已由原文确认，且比我判断的更脆。** 1202-1204 是 `检查是否已存在 → 已存在则返回 → 不存在则写入`。12.2（1214-1218）只声明不变量，不给实现。真正的问题在 1116 行：索引清单里写的是 `Messages.SenderId, Messages.ClientMessageId`，**没有 `UNIQUE` 字样**。`CLAUDE.md:63` 断言存在 `UNIQUE(SenderId, ClientMessageId)`，但已读到的方案文本并不支持这个断言。如果实际 DDL 只建了普通复合索引，那么 GPT Pro 提的「撞 UNIQUE 后回读」这一支根本不会触发，并发重试会静默产生两条消息。这是一次五分钟的 DDL 核对，但它是整条幂等链的地基。

**没有 outbox，所以周期同步不是优化项而是补偿机制。** 12.1 的顺序是提交事务（1205）→ 返回 `MessageDto`（1206）→ 推送 `NewMessage`（1207）。`DEC-001` 明确第一版不引入消息队列，也就没有出站日志。推送失败或进程在 1206 与 1207 之间崩溃，消息已入库但无人知晓；13.6（1400-1407）又规定关窗口保留进程与 SignalR 连接，意味着连接可以数天不重连。我第一次把定时拉取写成「建议，成本极低」，定级过低：在没有 outbox 的架构里，它是唯一的兜底路径。GPT Pro 把它列进必做项是对的。

**`source` 无语义已经在规格层面产出了确定的错误行为。** 12.3（1226-1234）的入库流程是 `插入 → 更新会话 → 判断是否通知`，没有 source 分支。按字面实现，History 加载旧消息会用一条旧消息覆盖会话的最后消息预览——这一条是确定的 bug，不是推测。通知侧同样成立：新设备首次登录后 History 加载最近若干条，本地 `IsNotified` 全为 false，只要不是当前前台会话，13.1 的四个条件全部满足，会逐条弹通知。我第一次说 History「必须既不通知也不推进游标」，方向对，但没指出规格已经在 12.3/13.1 里写死了错误路径。

**冷启动通知风暴由 13.2 的排除清单直接坐实。** 1324-1332 的不通知条件里有「用户彻底退出客户端」，没有任何一条覆盖「批量补拉」。用户彻底退出一晚再启动，200 条消息全部满足 13.1；13.3（1338-1344）每条都要放提示音、必要时闪烁任务栏。这不是通知多了 200 条，是 200 次声音。

**全局游标与会话可见性的错配确认存在，并且比我说的更棘手。** 1250 的可见性在查询时按当前权限计算。用户被加入一个已存在的私有频道后，`MessageId` 小于当前游标的历史消息永远不会被 sync 覆盖。方案没有任何地方说这部分由 History 负责。§3.2 会说明为什么 GPT Pro 的 `nextCursor` 方案**扩大**了这个盲区。

## 三、GPT Pro 的服务端扫描游标：评估与细化

### 3.1 接受的核心

GPT Pro 指出我的「连续无空洞才推进」判据不成立，理由正确：全局 `MessageId` 序列包含用户无权访问的其他会话消息，可见 ID 天然稀疏，客户端**无法**区分「合法空洞」与「漏掉的消息」。这个判据必须撤回。改由服务端返回独立的 `nextCursor`，表示服务端已安全扫描到的位置，而不是最后一条可见消息的 `MessageId`——这是正确的形状。

### 3.2 必须补足的三处

**（一）`nextCursor` 的取值要分两支写清，否则「安全扫描位置」是一句无法实现的话。**

- `hasMore == true` 时：`nextCursor` = 本页最后一条返回消息的 `MessageId`。安全，因为过滤条件在 `MessageId` 上单调。
- `hasMore == false` 时：`nextCursor` = 同一读事务内 `SELECT MAX(MessageId) FROM Messages` 的结果。不能取「响应时刻的当前最大值」。

**（二）分页查询与 `MAX()` 必须在同一个读事务（同一快照）内。** 如果分成两次独立查询，在两次之间提交的消息会被 `MAX()` 看到而不被页查询返回，那条消息永久漏掉。SQLite WAL 下开一个 deferred 读事务即可获得快照；EF Core 需要显式 `BeginTransaction`，不能依赖两次隐式查询。GPT Pro 没有提这一点，而这是整个 `nextCursor` 方案唯一的正确性证明依赖。

**（三）`nextCursor` 不解决提交乱序，两者必须一起写进前提。** 若 `MessageId` 是 INSERT 时分配的自增整数而可见性发生在 COMMIT，并发写入下 ID 100 可以晚于 101 提交。读事务看到 101 未看到 100 时，`nextCursor` 无论取哪一支都会跳过 100。`nextCursor` 是必要条件，不是充分条件；充分性来自 SQLite 单写者串行化。GPT Pro 在执行清单第 8 项列了「SQLite 单写者是第一版同步模型的前提」，但没有把它和 `nextCursor` 的正确性绑在一起。这两条必须写在同一段，否则将来有人「为了性能」开第二个写连接时，看不出自己动的是同步模型的地基。

**顺带一条明确禁止：** 1117 行有 `Messages.CreatedAt` 索引。同步游标不得使用 `CreatedAt` 或任何时间戳，时钟回拨与同秒并列都会破坏单调性。

### 3.3 关于 `MAX()` 型游标的一个反效果：它扩大了后加入会话的盲区

这一点两份评审都没意识到。首次同步时若用户在任何会话都没有可见消息，而库里已有 10000 条他人消息，`hasMore=false`，`nextCursor=10000`，客户端存下 10000。此后被加入私有频道，所有 `MessageId < 10000` 的历史永远不会被 sync 覆盖。

而如果游标停在「最后一条可见消息」（即不推进），加入后再同步反而会碰巧捞回那部分历史。也就是说：**`MAX()` 型游标在效率与确定性上更好，代价是把「后加入会话的历史」完全推给 History 加载**。

我仍然推荐 `MAX()` 型游标（依赖「碰巧」不是设计），但必须同时把补齐路径写成硬要求：`ConversationDto` 或 sync 响应需携带该成员的加入水位（如 `joinedAtMessageId`），客户端据此判定该会话需要一次 History 回填，而不是指望游标覆盖。这条不写，问题就会以「新人看不到频道历史」的形式在上线第一周出现。

### 3.4 本地事务语义的细化

GPT Pro 的表述是「只有一次完整的 Sync 页面成功落入本地数据库后，才提交同步游标」。方向对，但落到 SQLite 上还差四条：

1. **原子性。** 本页所有消息插入与 `LocalAppState` 中 `LastSyncedMessageId` 的 upsert 必须在**同一个本地事务**内提交。分开提交就有崩溃窗口。
2. **不能同事务时的方向性。** 若因实现原因无法同事务，必须**先提交消息、后提交游标**。游标滞后是安全的——12.3（1226-1229）按 `MessageId` 去重，重复处理无副作用；游标超前是永久丢失。这个顺序是不对称的，必须写明。
3. **部分失败整页回滚。** 本页任一消息因非「重复」原因插入失败，整页回滚，保持原游标重试。不允许「跳过坏消息、推进游标」。
4. **通知与副作用移出事务。** 13.3（1338-1344）把「写 `IsNotified = true`」放在弹通知之前、和放音闪烁托盘并列。这些必须全部在事务**提交之后**执行：否则事务回滚会留下一个指向不存在消息的通知，而 `IsNotified` 的置位又被回滚，状态自相矛盾。

第 4 条还牵出 13.3 自身的一个顺序缺陷，见 §4.5。

另有一条来自 `LocalAppState` 实际形状（1172-1176：`Key TEXT PRIMARY KEY / Value TEXT NOT NULL / UpdatedAt TEXT NOT NULL`）的具体要求：游标以文本存储，必须严格按 int64 解析；**缺失或不可解析时视为 0 并记警告，绝不允许回退成「当前最大值」**。把无效游标当作最大值是最容易写出的一行防御代码，也是最彻底的永久漏拉。

### 3.5 参数命名：不要在协议里制造分叉

GPT Pro 提议改成 `GET /api/sync?cursor=xxx&limit=100`。名字本身没问题，但 1247 行现有契约是 `afterMessageId`，本地键名也是 `LastSyncedMessageId`，静默改名会让方案、`CLAUDE.md:69` 和实现三处不一致。第一版建议保留 `afterMessageId`（int64）并新增 `limit`，响应体采用 `{ messages, nextCursor, hasMore }`。若将来游标变成复合结构，那是一次协议版本升级，按 `DECISIONS.md:3` 的范围本来就该单独立项。

### 3.6 行为矩阵：接受表格，拒绝把通知策略绑定到触发源

GPT Pro 把 `Sync` 拆成 `Sync-Reconnect / Sync-Periodic / Sync-Startup` 三个枚举值。这实际是改 12.5（1266-1273）的枚举定义，并且它把通知策略硬编码进了触发源，产生两个问题：`Sync-Periodic` 那一格写的是「按规则提醒」——规则未定义；而「断线 8 小时后重连拉回 300 条」按它的表会走「聚合提醒」，「启动拉回 3 条」会走「只发汇总」，两者都不合直觉。

更稳的切法是把两个正交的东西分开：

- `IncomingMessageSource` 保持 4 值（`Realtime / Sync / History / SendResponse`），只决定**入库语义**：是否插入、是否计未读、是否推进游标、是否更新会话预览。
- 另设 `NotificationPolicy { PerMessage, Aggregate, Suppress }`，由调用方按**本批数量与跨会话数**决定，阈值统一（建议单批 > 10 条或跨 > 3 个会话则聚合）。

这样 `Sync-Periodic` 自动有了定义，「重连拉回 300 条」和「冷启动拉回 300 条」得到一致处理，枚举也不必扩张。GPT Pro 表格里 `History` 全否、`SendResponse` 走「更新临时消息」这两行直接采纳。

## 四、GPT Pro 未覆盖的剩余风险

### 4.1 自己发的消息会在本地产生两行——纯规格层面即可证明

1199 行：客户端先插入本地 `LocalMessages`，状态 `Sending`，此时只有 `ClientMessageId`，没有服务端 `MessageId`。1227 行：接收去重的判据是「`LocalMessages` 已存在 `MessageId`」。两者对不上：服务端消息回来时（无论走 `SendResponse` 还是 `Realtime`）都匹配不到那条 pending 行，于是插入第二行。这是确定的重复显示。

1209 行写「其他客户端收到 `NewMessage` 后入库和通知」，但 12.1 没有规定推送时如何排除发送者。SignalR 的 `Clients.Group(...)` 默认**包含**发送者自己的连接；要排除得显式用 `OthersInGroup`。而多设备场景下，发送者的**其他**设备必须收到。所以正确规则是：向整组广播（包含发送者的所有连接），客户端 `Realtime` 分支先按 `(自己, ClientMessageId)` 匹配本地 pending 行，命中则更新为 `Sent` 并补 `MessageId`，未命中才插入。

这要求 `MessageDto` 携带 `ClientMessageId`。第 8 节未读到，标 `需要探针`。若 DTO 不含该字段，去重只能靠时间窗启发式，那是不可接受的，必须改协议。

### 4.2 17.2 的可调上限与 19.3 的静态 nginx 限制冲突

管理员在应用内把单附件上限调到 500MB（1692），nginx 仍是 `client_max_body_size 200m`（1839）。结果是 nginx 在请求体读完前返回 413 的 HTML 错误页，请求根本到不了应用，用户看到的既不是 14.1 的大小提示也不是应用错误码。必须二选一：要么把上限固定为部署常量（去掉 17.2 的可调项），要么写明「应用上限不得超过 nginx 配置值」并在管理端做校验与提示。同时客户端必须能识别裸 413 并给出可读文案。

### 4.3 `LIKE` 的三处具体缺陷

- **通配符未转义。** 1561/1567 直接拼接 `@keyword`。用户搜 `50%` 或 `a_b`，`%` 与 `_` 会被当作通配符，返回一堆无关结果。必须转义并加 `ESCAPE` 子句。
- **1122「可以为常用字段加普通索引」对 `LIKE '%kw%'` 无效。** 前置通配符无法使用 B-tree 索引，这句话会误导实现者以为加了索引就有性能。应删除或改成「前置通配符查询必然全表扫描，第一版接受，靠 `limit` 与会话过滤兜底」。
- **15.3 返回 `snippet`，但 `LIKE` 没有 snippet 能力。** FTS5 有 `snippet()`，`LIKE` 方案下摘要必须自己算：命中位置、前后截取窗口、多命中取哪一个、是否高亮。这是要写代码的，规格现在一个字都没有。

另外建议按 GPT Pro 的思路补一条退出阈值（消息量或实测 P95 延迟超过明确数值才重新评估搜索实现），这样将来没人会拿 Elasticsearch 去「修」它，撞上 `DEC-001` 的否决清单。

### 4.4 附件孤儿与未附着附件的鉴权空洞

14.1（1442-1450）是先上传附件拿到 `AttachmentId`，客户端发消息时再带上。两个后果：

- **孤儿文件。** 上传成功但消息从未发出（用户取消、崩溃、切走），`Attachments` 表与 `uploads` 目录留下无人引用的记录和文件，没有任何清理机制，也没有「附件必须属于某条消息」的约束。
- **鉴权空洞（安全）。** 14.3（1471-1478）的下载鉴权是「验证用户是否有权限访问该附件所属会话」。未附着消息的附件**没有所属会话**，这条规则无法求值。实现者最省事的写法是「查不到会话就放过」，于是任何登录用户拿到 `AttachmentId` 就能下载他人尚未发出的文件。必须显式规定：未被任何消息引用的附件，只有上传者本人可下载；并加 TTL 清理。

这条是 §1.2 撤回之后**新增**的附件问题，比原来那条被否证的更严重。

### 4.5 13.3 的写序会永久吞掉通知

1339-1340 的顺序是「写入本地数据库 `IsNotified = true`」然后「弹 Windows 通知」。若弹出失败（通知注册未完成、系统通知被关闭、API 抛异常），消息已被永久标记为已通知，用户再也不会收到提醒。同时 13.2（1331）把「Windows 系统通知被用户关闭」列为不通知条件——那么此时是否置位 `IsNotified`？规格没说。

建议：提交入库事务（`IsNotified = false`）→ 弹通知 → **弹出成功后**再置 `IsNotified = true`。崩溃最多导致一次重复通知，优于永久静默。系统通知被关闭时不置位，但也不补历史通知（重新开启后只按新消息通知）。这三句必须写进规格，否则两个实现者会做出两种失败模式。

### 4.6 13.7 的「第一版只用 Mutex」与 13.4 的跳转参数直接矛盾

13.4（1353、1362-1363）要求通知携带 `conversationId + messageId`，点击后切换到对应会话并滚动到对应消息。13.7（1424-1431）说「可使用 Mutex 或 Named Pipe」「第一版可以只用 Mutex + 激活窗口」。

Mutex 只能阻止第二个实例，**无法把激活参数交给第一个实例**。而 13.2（1330）规定用户彻底退出后不通知，所以点击通知时进程一定在运行——正好落在「第二实例被挡住、参数无处可去」的场景。第一版必须是 Mutex **加**一条 IPC 通道（Named Pipe 或通知激活直接投递），不能只用 Mutex。这是规格内部矛盾，不是实现细节，必须改 13.7。这一条也是 §7.3 探针必须回答的问题。

### 4.7 免打扰在规格里没有落点

13.1（1312）把「客户端未处于免打扰」写进了触发条件，但 1180-1188 的 `LocalAppState` 必存键清单里没有免打扰状态，也没有任何地方定义它的范围（全局／按会话／时间段）和存储位置。这是一个被引用但未定义的状态。第一版可以只做全局开关，但必须写下来并加进必存键。

### 4.8 备份仍是 `未验证` 缺口，且 GPT Pro 的备份命令是错的

17.3（1696-1705）确实展示了「数据库文件大小」与「附件目录大小」，所以**可见性是有的**——我第一次说「没有任何监测」不准确。缺的是阈值与动作。

至于备份：已读到的 19.3/19.4 部署配置里没有备份要求，第 20-24 节未读到，所以这条维持 `未验证`，不能断言方案完全没写。但 GPT Pro 给的「每日备份 `relaycove.db`」需要修正：**运行中的 WAL 模式 SQLite 不能直接 `cp`**，会得到缺 WAL 内容或不一致的副本。必须用 `sqlite3 relaycove.db ".backup"` 或 `VACUUM INTO`，且备份文件与 `uploads` 的时间点要对齐（附件先备份、库后备份，可以容忍库里引用的附件已存在；反序会出现引用不到文件的记录）。

### 4.9 已读状态的多设备语义未定义

12.6（1292-1297）打开会话时清本地未读并 `POST /api/conversations/{id}/read`，但没有说服务端已读状态如何回传给同一用户的其他设备，也没有定义本地 `IsRead` 与服务端已读水位的关系。第一版完全可以选择「不同步已读」，但必须写明，否则跨设备未读数长期不一致会被当成 bug 反复返工。

## 六、事实、假设与待探针的分界

**已验证（有行号证据）：** 12.1 为先查后插；12.2 只声明不变量；12.3 去重按 `MessageId` 且无 source 分支；12.4 无推进规则、无分页、仅重连触发；12.5 枚举无语义；12.6 未读条件无 source 守卫；13.1-13.3 无批量例外且写序有缺陷；13.7 允许只用 Mutex；14.1-14.3 附件流程与鉴权口径；15.1-15.4 搜索已定 `LIKE` 且要求服务端过滤；17.2/17.3 管理端能力与状态展示；19.3/19.4 nginx 与应用上限；1116-1119 索引清单未标 UNIQUE；1170-1188 `LocalAppState` 为 KV 表且含两个游标键；阶段 0 验收为 `dotnet build` 必须通过；`DECISIONS.md` 只有 `DEC-001`/`DEC-002`；`WORKFLOW.md` 记录环节不含 `DECISIONS.md`；`STATUS.md:9` 自指。

**假设（推理，未见原文）：** `MessageId` 为 64 位单调自增整数；SQLite 默认单写者足以保证提交顺序与 ID 顺序一致；`LocalConversations` 含按会话的通知开关（13.1 隐含要求）；非打包 WPF 使用 Windows 通知需要 Windows App SDK 引导与 AUMID／COM 激活器注册。

**需要探针（必须查或必须跑）：** 第 11.1 `Messages` DDL 中 `MessageId` 类型与是否存在 `UNIQUE(SenderId, ClientMessageId)`；第 8 节 `MessageDto` 是否含 `ClientMessageId`、`/api/sync` 现有响应形状；第一版是否支持撤回／编辑／删除；第 20-24 节是否已有备份与磁盘阈值要求；通知激活与单实例传参的实测结论（§7.3）。

## 七、修订后的执行计划与验收标准

顺序与 GPT Pro 一致：规格 → 脚手架 → 探针。差别在于我把 DDL 与协议核对前置进第一步（它决定幂等方案能否成立），并把每一步的验收写成可判定的条件。

### 7.1 第一优先：DDL／协议核对 + 规格补丁 + `DEC-003`

先做 30 分钟的只读核对（第 11.1、第 8 节），产出三个结论：`MessageId` 类型、是否已有 UNIQUE、`MessageDto` 是否含 `ClientMessageId`。这三项任何一项为否，都会改变下面的写法。

规格补丁的验收条件（逐条可检查）：

- **11.1**：出现 `UNIQUE(SenderId, ClientMessageId)`；`MessageId` 明确为 64 位单调自增整数。若原本没有，作为变更记入 `DEC-003` 影响面。
- **12.1 重写为 INSERT-first**：包含冲突回读分支；新建返回 201、重放返回 200；重放**不再推送** `NewMessage`；推送发生在事务提交之后，推送失败只记日志、不回滚、不影响响应；`ClientMessageId` 规定为标准 GUID 并在服务端校验格式。
- **12.4 重写**：`GET /api/sync?afterMessageId=&limit=`，响应 `{ messages, nextCursor, hasMore }`；写明 `nextCursor` 的两支取值；写明「页查询与 `MAX(MessageId)` 必须在同一读事务内」；写明客户端循环至 `hasMore=false`。
- **新增 12.7 本地写入与游标语义**：消息插入与 `LastSyncedMessageId` 同事务；不可同事务时先消息后游标；整页回滚重试同一游标；游标解析失败视为 0 并告警，禁止回退为最大值；通知／放音／闪烁／托盘计数一律在提交后执行。
- **新增 12.8 来源行为矩阵**：六列（入库／未读／通知／推进游标／更新会话预览／声音与闪烁）× 四个 source 值全部填满；`History` 与 `SendResponse` 明确为不通知、不计未读、不推游标、不更新会话预览；12.6 与 13.1 各补一句「仅当 `source ∈ {Realtime, Sync}`」。
- **新增自发消息 echo 规则**：服务端向整组广播（含发送者其他连接）；客户端 `Realtime`／`SendResponse` 分支先按 `(自己, ClientMessageId)` 匹配 pending 行再决定更新或插入；`MessageDto` 必须含 `ClientMessageId`。
- **新增同步触发时机**：重连成功、客户端启动、主窗口重新激活、60 秒定时；四者共用同一 sync 流程；**同一时刻只允许一个 sync 在跑**（互斥 + 触发合并）。
- **新增 13.8 通知聚合与冷启动抑制**：`NotificationPolicy` 三态与阈值（建议单批 > 10 条或跨 > 3 个会话）；`IsNotified` 为逐条权威判据，`LastNotifiedMessageId` 为聚合边界游标，不得回退，且不变量 `LastNotifiedMessageId <= LastSyncedMessageId`；修正 13.3 写序为「提交 → 弹出 → 置位」；系统通知被关闭时不置位、不补历史通知；免打扰状态加入 `LocalAppState` 必存键并定义为全局开关。
- **新增后加入会话的历史归属**：sync 前向游标不回溯；成员加入水位随 `ConversationDto` 下发；客户端据此对该会话做一次 History 回填。
- **新增前提声明**：第一版同步模型依赖 SQLite 单写者串行化；引入第二个写连接、启用多写或更换数据库都需重新设计游标，属协议级变更。
- **13.7 修正**：第一版为 Mutex + IPC（Named Pipe 或通知激活直投），删除「可以只用 Mutex + 激活窗口」。
- **15.4 修正**：关键词转义 `%`／`_` 并使用 `ESCAPE`；定义 snippet 生成规则（截取窗口、多命中取首个、是否高亮）；`limit` 给上限与服务端超时；删除或改写 1122 关于普通索引的表述；补 `LIKE` 的退出阈值（消息量或 P95 延迟的明确数值）。
- **14.x 修正**：未被任何消息引用的附件仅上传者可下载；孤儿附件 TTL 清理；17.2 的可调上限不得超过 nginx `client_max_body_size` 并在管理端校验；补 413 的客户端可读提示路径。
- **部署补充**：每日 `sqlite3 .backup` 或 `VACUUM INTO` 备份数据库（禁止直接 `cp` 运行中的 WAL 库）；uploads 备份先于数据库；保留 7-14 天；磁盘占用 > 80% 告警，挂到 17.3 已有的两个大小指标上。
- **决策记录**：新增 `DEC-003 消息同步与通知语义`、`DEC-004 第一版搜索固定 LIKE 及退出阈值`；`WORKFLOW.md` 的「记录与提交」加一行——本任务若改变协议、数据库或兼容性，必须更新 `DECISIONS.md`。

理由：这些全部是规格缺口，不是代码缺口。现在写要几小时；留到实现期，`WORKFLOW.md:87-94` 要求的同步与通知独立复核将无标准可依，只能变成风格审查。

### 7.2 第二优先：阶段 0 脚手架，含负向验证

验收条件：

- `RelayCove.sln` + 四个项目 + `tests/<Project>.Tests`；`dotnet build` 在 Debug 与 Release 均成功。
- `global.json` 固定 SDK `10.0.101`，`rollForward` 限同 feature band 补丁。
- `Nullable enable`、file-scoped namespace、四空格等约束通过 `Directory.Build.props` / `.editorconfig` 生效，并用**一个故意违规的样例**证明分析器真的会报错，而不是只声明配置。
- `scripts/verify.ps1 -Mode Fast|Full` 存在且可运行；`Full` 包含 `dotnet format --verify-no-changes`、Release 构建、全部测试、`git diff --check`。
- **负向验证（这一条是本步骤的核心）**：三次人为破坏各自导致非零退出且输出能定位原因——(a) 引入编译错误；(b) 引入格式违规；(c) 引入失败断言的测试。三次 `Full` 都必须失败，`Fast` 至少在 (a)(c) 失败。结果记入任务日志。没有这一条，产出的正是 `CLAUDE.md:9` 与 `WORKFLOW.md:52` 明令禁止的「总是成功」的脚本，而且不会有人发现。

### 7.3 第三优先：通知激活 + 单实例传参探针（限时，用完即弃）

必须回答的判定点：

- 非打包 WPF 应用能弹出携带 `conversationId` / `messageId` 的 Windows 通知。
- 应用在运行、窗口已隐藏到托盘时，点击通知 → 窗口显示、取消最小化、置前、日志打印出两个参数。
- **第二个实例被单实例机制阻止时，参数仍能到达第一个实例并触发跳转。** 这是 §4.6 那处矛盾的判决点。如果 Mutex-only 做不到（预期做不到），结论必须写成「第一版必须 Mutex + IPC」，并据此修改 13.7。
- 明确记录：是否需要 Windows App SDK 引导；是否需要 AUMID 与 COM 激活器注册；注册必须由安装包完成到什么程度；对 3.5 的「下载完整安装包 → 启动安装器 → 装完重启」流程与开机自启是否有影响。
- 若通知激活对应用身份有硬要求，输出对安装包形态（MSIX 与传统安装器）的结论并记 `DEC-005`。
- 探针代码不留在 `RelayCove.Client` 里，结论写进任务记录。

## 九、Codex 二次评审与最终裁定

### 9.1 对 Claude 二审的事实校正

Claude 二审的可靠性推导总体成立，但它仍未读取完整协议和 DDL，因此两项“需要探针”已经可以由仓库直接裁定：

- **已验证：** `RelayCove_工程落地方案.md:1062-1073` 已定义
  `Id INTEGER PRIMARY KEY AUTOINCREMENT` 和
  `UNIQUE(SenderId, ClientMessageId)`。因此裁定表第 13 项不再是未知项；
  真正需要修改的是把 12.1 的 check-then-insert 改为 INSERT-first，并以唯一约束冲突作为幂等分支。
- **已验证：** `RelayCove_工程落地方案.md:930-940` 的 `MessageDto`
  已包含 `Guid ClientMessageId`。裁定表第 31 项也已解决，客户端可以用
  `(SenderId, ClientMessageId)` 将 pending 行与 `SendResponse`／Realtime 回声合并。

另外，`ConversationMembers.JoinedAt` 已存在，但没有定义成员加入后的历史可见范围；
`Messages.EditedAt`／`DeletedAt` 已存在，但没有对应消息编辑、撤回接口。第一版应明确
后者为非目标，避免为了游标传播未来功能而扩大当前范围。

### 9.2 必须在脚手架前落定

| 主题 | 最终裁定 |
| --- | --- |
| 同步游标 | 接受服务端扫描水位；客户端不得使用最后一条可见消息推算。输入、响应和本地键统一使用 `cursor`、`nextCursor`、`LastSyncCursor`，第一版值为 `long`，但语义属于服务端。 |
| 服务端一致性 | 分页查询和 `nextCursor` 必须来自同一个读事务；`hasMore=false` 才可把水位推进到该快照的全局最大消息 ID。同步正确性明确依赖 SQLite 单写者。 |
| 客户端一致性 | 整页消息和游标在一个本地事务中提交；任一非重复错误导致整页回滚；通知、声音、闪烁只在提交后执行。 |
| 并发同步 | 启动、重连、窗口激活和定时检查共用一个 single-flight 流程，后续触发只合并一次待执行请求。 |
| 消息幂等 | INSERT-first；唯一冲突后回读并返回 200，不再次推送；新消息返回 201。`ClientMessageId` 必须是合法 GUID。 |
| 来源与通知 | 保留四种 `IncomingMessageSource`，另设通知策略；不要把启动、重连、周期同步继续膨胀成 source 枚举。 |
| 单实例激活 | Mutex 只负责判重，通知跳转参数必须通过 IPC 送达已有实例；阶段 0 探针负责选择具体机制。 |

这里唯一不应直接固化的是 Claude 建议的“超过 10 条或 3 个会话”阈值。它缺少产品证据。
第一版可以先按场景确定规则：实时逐条、后台重连少量逐条、冷启动汇总、用户主动打开时
只更新未读；数量阈值应做成可测试的配置或常量，而不是架构决策。

### 9.3 接受，但不阻塞第一次构建

- 搜索的 `%`／`_` 转义、snippet 规则和前置通配符全表扫描判断正确，应写入搜索规格；
  不需要现在引入 FTS5、Elasticsearch，也不应阻塞阶段 0 脚手架。

- `LastNotifiedMessageId` 必须二选一：赋予“汇总通知处理水位”的唯一语义并写出不变量，
  或从必存键删除。不能让它与逐消息 `IsNotified` 同时充当真源。
