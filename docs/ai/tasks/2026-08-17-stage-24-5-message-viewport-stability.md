# Stage 24.5 — 私信切换最新页与消息视口稳定性（工作日志）

- Status: completed and delivered by the `main` commit containing this record
- Starting point: `main@1712d36`
- Date: 2026-08-17 CST
- Scope: `RelayCove.App` 会话激活与原生消息列表；不修改 Web、Core 协议、Data、服务端或部署

## 用户现象

1. 首次打开或切换私信时，有时显示最早/中段消息，而不是最新消息。
2. 同一个会话手动滚到最新，切走再回来仍可能回到中段。
3. 表现不稳定：同一路径有时正确、有时错误，单元测试和预览数据不容易复现。

## 正式客户端复现

使用未设置 `RELAYCOVE_NATIVE_UI_PREVIEW` 的正式 Debug 客户端，恢复既有真实 Realm 会话，并把窗口固定在 `DISPLAY2`。本轮没有发送或修改消息；正常历史/event 读取以及既有自动标读可能提交已查看消息的 flags。

- 初始 `fan`：98.92%，最后可见消息为 17:44。
- 第一次进入 `zhang`：79.39%，最后可见消息停在 16:12。
- 第二次进入 `zhang`：69.90%，最后可见消息停在 15:25。
- 手动把 `zhang` 滚到 100%，切到 `fan` 再返回：70.37%，最后可见消息退到 13:47。

这证明消息已经在本地/服务器页中，故障发生在会话激活后的原生视口定位，不是历史消息缺失。

## 根因

### 1. 激活滚动身份跨访问错误复用

`ShellViewModel` 用会话键、history generation 和目标消息 ID 去重激活滚动。同一缓存页重新进入时，这三项可能完全不变，导致新访问被误判为上一次已完成的滚动，从而保留上一会话的原生绝对偏移。

### 2. 虚拟列表过早确认

WinUI `CollectionView` 的最后一个容器已实现时，后续消息行仍可能继续测量并扩大 `ExtentHeight`。如果此时立即确认并显示，用户会先看到中段或旧偏移。此前的全局 `LayoutUpdated` 保底虽然能追到底部，却会在发送和其他布局变化时重复 `ChangeView`，造成整块消息区闪动，因此不能恢复。

## 修复

- 每次 `BeginNavigation` 清除上一访问的 activation-scroll identity；相同缓存会话也必须获得新的滚动请求。
- 会话激活实现并定位最后一项后立即显示，不再等待固定时间。只要用户没有主动向上滚，后续原生行高变化都继续把视口锚定到最新消息；滚轮、滚动条或滚动键输入会立即解除底部锚定。这符合聊天工具“位于最新消息时持续跟随、用户主动离开后停止跟随”的常规语义。
- 激活定位期间消息列表保持透明且不可交互；确认稳定后一次显示，避免展示错误中间帧。
- `RealtimeFollow` 不进入激活稳定循环，继续保持列表可见，避免重新引入发送闪屏。
- 保留 `KeepScrollOffset` 和 older-page 的消息 ID + DIP 锚点；它们只服务集合更新/向上分页，不代替会话激活语义。

## 已知边界与门禁

- 首次加载和缓存切换不再等待300ms；首次到底即显示，随后由底部锚定吸收虚拟布局变化。older-page prepend 属于独立分页锚点时序，用户主动向上滚时已经解除最新消息锚定，不得混入 realtime 路径。
- 本轮真实窗口属于导航验收，不是 `verify.ps1 -Mode Live`，也没有消息发送、编辑、删除、reaction 或收藏写入；正式客户端的既有自动标读仍可能提交已查看消息的 flags。
- 未运行 Full、打包、部署、干净 VM、100%/200%、高对比或人工密码登录；Stage 21 外部门禁继续保留。

## 可复用经验

1. 原生虚拟列表要按“访问实例”管理滚动意图，不能只按业务资源键永久去重。
2. 目标容器实现、滚动条到达底部和最终布局稳定是三个不同阶段。
3. 会话激活、实时追加、向上分页必须使用独立状态和确认条件。
4. Preview 适合视觉排版，不足以覆盖真实消息高度、缓存页和原生虚拟化时序；滚动缺陷必须在 formal non-preview 客户端复现。
5. 真实验收同时记录百分比与首/末可见消息，比只看截图或只看单元测试更可靠。
