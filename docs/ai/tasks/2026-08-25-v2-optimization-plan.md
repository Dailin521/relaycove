# RelayCove 第二版（V2）优化计划：先稳后优

Status: approved planning baseline; ordered optimization sequence not started

- Created: 2026-08-25
- Product scope: `RelayCove.App` MAUI Windows only
- Functional baseline: Stage 30 delivery `main@57c8145`
- Repository baseline at plan creation: `main@6e8d0e9`

本文中的“V2”指第二个 MAUI 开发优化周期，不预先决定下一个语义版本号、tag 或发布形式。

2026-08-25 用户在计划序列前单独插入并确认了 Stage 31“Windows 消息正文鼠标拖选”，随后单独提出 Stage 32“MAUI 收藏消息入口”、Stage 33“Windows reaction 按钮裁切”和 Stage 34“reaction 表情面板定位”。这些都是独立确认、独立交付的窄 UI 修正，不改变下文从搜索正确性开始的既定顺序或范围。

2026-08-25 用户授权将已经交付的 Stage 31–36 增量收口并发布为 `v2.1.0`；当日已完成正式 GitHub Release。这是一次发布检查点，不代表下文六部分优化序列已经全部实施或 V2 总计划已经完成；未完成项继续保留。

## 1. 目标与执行方式

V2 只优化第一版已经交付的聊天能力，不增加新的聊天产品范围。实施顺序固定为：基线整理、搜索正确性、写入结果确认、群资料可靠性、Windows 桌面体验、定向性能优化。前一项的状态、回归测试和必要文档没有收口前，不开始后一项。

每次仍只处理用户明确提出并可独立验证的一个问题。纯逻辑、协议和缓存问题由 Agent 运行最小确定性测试；视觉、焦点、鼠标、键盘、字号和 DPI 改动由用户通过 Visual Studio 快速人工确认。只有用户明确要求时才执行对应问题的最小提交与非强制推送。

本计划继续遵守以下边界：

- Zulip 是账号、权限、群资料、成员和消息的唯一权威来源；不增加 RelayCove 服务端、代理或第二消息后端。
- 只维护 MAUI；不修改 `RelayCove.Web`，不恢复公开频道、命名话题、多人私信或旧频道兼容入口。
- 保持现有消息窗口、SQLite schema/账号隔离、未读投影和滚动状态机；不重写 Core reducer，不进行大型 `ShellViewModel` 拆分。
- 非幂等写入绝不自动重试。普通开发不运行 Live、不执行真实 Realm 写入、不打包、不发布、不部署。
- 工作树中的所有 `.verify/` 目录保留在本机，不删除、不清理、不暂存、不提交。

## 3. 搜索正确性

### 3.1 本机与服务器结果合并

- 同一真实消息可能同时来自本机投影和 Zulip 服务器搜索。合并时以非空真实 `messageId` 为唯一去重键，不以会话键、标题、摘要或对象实例去重。
- 同一 `messageId` 冲突时，本机当前投影是显示内容、编辑/删除状态、发送者和会话归属的优先来源；服务器结果只补足本机没有的历史命中和分页发现信息。
- 不同 `messageId` 即使属于同一会话、同一发送者或正文相同，也必须保留为不同消息命中。
- 消息命中的稳定 UI key 统一为 `message:{messageId}`；普通会话入口继续使用规范会话键。

### 3.2 独立取消通道

- 在 Core 增加明确的 `MessageSearchLane`（至少 `Global` 与 `ConversationList`），并让 `IClientSession.SearchMessagesAsync` 按 lane 管理独立的 generation/取消源。
- 左侧统一会话搜索只能取消上一轮左侧请求；右侧聊天全局搜索只能取消上一轮右侧请求。任一侧的新输入、清空或分页都不得取消另一侧正在运行的请求。
- App 现有 `_conversationFilterCancellation` 与 `_searchInputCancellation` 继续负责各自 UI 生命周期；Core 的账号/run epoch 仍拒绝注销、重连或账号切换后的晚到结果。

### 3.3 呈现与回归

- `ConversationListItem` 增加明确的消息命中状态，消息命中行显示“消息匹配”标识，并把该状态加入可访问名称；普通会话匹配不显示该标识。
- 不改变 Stage 25 支持会话边界和现有服务器分页规则。
- 回归至少覆盖：本机/服务器同 ID 只显示一行、本机最新状态优先、同会话不同 ID 全部保留、左右搜索互不取消、旧 query/旧账号结果被丢弃、分页去重，以及点击结果仍定位精确消息。

## 4. 写入结果确认

### 4.1 统一结果类型

Core 增加统一的 `AuthoritativeWriteOutcome`，供当前 MAUI 产品中的群名、群公告、群置顶和静音使用。对 UI 只暴露三种确定含义：

| 状态 | 含义 | UI 行为 |
|---|---|---|
| 已确认成功 | 原请求正常确认，或唯一一次权威读取确认服务器值等于请求值 | 应用权威值并关闭/刷新对应编辑状态 |
| 服务器仍是原值 | 唯一一次权威读取确认服务器值仍等于写入前捕获值 | 不投影请求值，保留用户输入并明确提示未生效 |
| 结果仍无法确认 | 权威读取失败、返回第三种并发值，或账号/会话已切换 | 禁止旧结果回填，保留用户输入并提示用户检查当前状态 |

结果可以记录确认来源（原响应或 readback）和面向 UI 的安全错误分类，但不得包含凭据、原始响应或敏感服务器内容。

### 4.2 非幂等写入流程

1. 发起写入前捕获账号 ID、Realm、session/run generation、目标频道/偏好和原值。
2. 原写请求只发送一次，绝不因超时、断线、5xx 或异常 2xx 自动重发。
3. 正常且可验证的 Zulip success 响应直接返回“已确认成功”。
4. 超时、连接中断、5xx 或缺少/损坏成功契约的异常 2xx 只允许执行一次对应目标的权威 GET。
5. readback 等于请求值时返回“已确认成功”；等于捕获原值时返回“服务器仍是原值”；读取失败或出现第三种值时返回“结果仍无法确认”。
6. 明确的 4xx/403/429 仍走现有确定失败处理，不进行隐藏 readback，也不改写为结果未知。
7. 任一阶段发现账号、Realm、run generation 或当前目标会话已变化，立即丢弃晚到投影；旧结果不得覆盖新账号或新会话。

`IClientSession.UpdateChannelAsync` 与 `SetSubscriptionPreferenceAsync` 改为返回统一结果，Shell 与群设置界面共用一套结果处理。只有“已确认成功”可以更新本地成功态；其他状态不得先乐观投影再回滚。

### 4.3 回归

- 每种模糊结果都精确验证一次写入、最多一次 readback、零自动重试。
- 覆盖直接成功、readback 后成功、服务器原值、第三种并发值、readback 失败、异常 2xx、5xx、断线、超时、明确 4xx，以及账号/会话切换时禁止回填。
- Zulip.Client 验证请求次数和响应分类；Core 验证三态结果与投影；App 验证统一提示和输入保留。

## 5. 群资料可靠性

### 5.1 完整可见成员目录

- 打开“新建群聊”时先立即显示 register/本机已知的活跃用户，同时发起一次有界、只读的 `GetRealmUsersAsync`，读取当前账号完整可见成员目录。
- 以 user ID 合并并去重，只展示可发起会话的活跃成员；不得把同名用户合并，也不得把旧账号目录带入新账号。
- 请求捕获账号、Realm、弹层 generation；弹层已关闭、重新打开或账号已切换时，晚到结果不得覆盖当前候选列表。
- 权威读取失败时保留已知候选并明确说明列表可能不完整，不阻塞已有聊天，也不伪装成完整目录。

### 5.2 群成员短期缓存

- 为群成员头像、人数和成员名搜索增加账号隔离的短期缓存。默认 TTL 为 5 分钟；同一轮刷新最多并行 4 个频道成员请求，Realm 用户目录在一轮刷新中共享一次结果。
- 缓存键至少包含账号 ID、Realm 和 channel ID；数据保存成员 ID 与显示所需的最小用户资料，不成为服务器成员关系的第二权威源。
- 邀请、移人、转让完成后立即把对应群缓存标记为过期；打开群设置时强制进行一次权威刷新；群详情取得更新成员关系时覆盖旧缓存并重置 TTL。
- 刷新失败保留上次成功数据；从未成功加载时继续使用群名首字头像和已知人数回退。任何成员读取失败都不得阻塞消息历史、实时接收或发送。

### 5.3 回归

- 覆盖完整目录合并、ID 去重、停用用户过滤、弹层/账号晚到结果、TTL 命中与过期、成员变更后的 dirty refresh、并发上限、失败保留旧值和首字回退。

## 6. Windows 桌面体验

本节分成独立问题逐项实施和人工确认，不在一个未验收改动中同时叠加。

### 6.1 底部新消息提示

- 复用现有 `NewMessageCount`。值为 1–99 时显示“`N 条新消息`”，超过 99 显示“`99+ 条新消息`”。
- `NewMessageCount` 只表示用户离开底部后实时到达的消息数，不替代 Zulip 总未读数。
- 当计数为 0、但当前位置离底部超过现有两页阈值时，仍显示“跳转到最新消息”。
- 只有实际打开对应会话并确认到达最新位置后才按现有门禁清零；悬停、任务栏预览或单纯获得窗口焦点不得清除。
- 可访问名称同时朗读数量和“跳转到最新消息”动作。

### 6.2 会话列表键盘与 Narrator

- Tab 可进入会话列表；Up/Down 移动相邻项，Home/End 到首尾，Enter/Space 打开当前焦点项。
- 搜索框按 Down 时只把焦点移到第一个结果，不直接打开会话。
- 焦点态与已选择会话态必须视觉可区分，并在浅色、深色和高对比下可见。
- Narrator 依次朗读标题、摘要、时间、消息匹配、未读数量、置顶和静音状态。置顶/静音不能只靠颜色或透明度表达；左栏补充可见静音状态。

### 6.3 弹层焦点返回

- 账户菜单无论通过选择、外部点击或 Escape 关闭，焦点都返回顶部头像按钮。
- 新建会话弹层取消、外部点击或 Escape 关闭后，焦点返回 `+`；成功新建并打开会话后，焦点进入 Composer。
- 使用独立的焦点请求 generation，防止旧弹层关闭事件把焦点从新界面抢回；不得对所有 `IsOpen=false` 状态变化盲目调用 Focus。

### 6.4 字号与 DPI

- 现有字号设置覆盖左栏标题/摘要与聊天头；如现有 token 不足，增加动态标题 token，不写死单独字号。
- 左栏行、聊天头和相关操作区的固定高度改成最小高度，使 11/14/18 字号和 Windows 100%/200% DPI 可以自然增高而不裁切。
- 人工检查至少覆盖 1440×900、640×900、长中文名称、`99+` 徽标、浅色/深色，以及高对比抽查。
- Agent 完成代码和最小构建后交给用户在 Visual Studio 验证真实窗口；未经单独要求不启动、移动、操作或截图用户窗口。

## 7. 定向性能优化

### 7.1 消息正文解析有界缓存

- 在 App 显示层为 `MessageContentPresentation` 增加有界 LRU，默认最多 512 项。
- key 固定包含账号 ID、Realm origin、消息稳定身份（真实 message ID；本地回声使用 local ID）和 raw 内容。只有这些值完全相同才复用引用、附件和表情短码解析结果。
- raw 内容、Realm 或账号变化必须重新解析；退出账号、清理该账号缓存或 ViewModel dispose 时清除对应条目。
- `MessageItem.Content` 继续是复制、编辑、引用和服务器对账的原始权威，不把 presentation 缓存持久化到 SQLite。
- 回归覆盖同 key 只解析一次、正文编辑重解析、Realm/账号隔离、本地回声身份和 LRU 淘汰。对 250 条不变消息重复投影时，每个唯一 key 的 parser 调用不超过一次；耗时/分配前后值只作记录，不设脆弱的机器绝对阈值。

### 7.2 统一会话行键化复用

- `ReconcileConversationListItems` 每轮先按稳定 `ProjectionKey` 建立旧行映射，再复用已有对象并只更新变化字段，消除逐项 `FirstOrDefault` 和重复扫描。
- 当前 MAUI 不消费的旧频道/话题列表不得在每次状态投影中重复构造；只删除已确认无消费者的冗余 App 投影，不改 Core reducer 或状态契约。
- 保持置顶优先、其余按最新消息排序，且不破坏已选行、焦点、未读/置顶/静音、搜索结果身份和滚动锚点。
- 回归覆盖 1000 行不变投影的对象复用、单行更新、插入/删除、筛选/搜索，以及无变化时不 reset 集合、不造成滚动跳变。

## 8. 验证、复核与交付

Stage 35 是用户在 V2 既定序列前单独插入的窄 UI 修正：MAUI 图片消息只显示受控预览框；右键具体图片时复用正常消息菜单并额外提供“下载原图”，普通文件卡片与受控下载边界不变。Stage 36 是随后单独提出的 Windows 托盘体验：常驻托盘图标、固定槽位的消失/出现提醒，以及不抢焦点的头像/正文/权威未读悬浮预览。Stage 37 只处理当前前台底部会话收到对方消息时，由临时未读分隔及随后服务器标读确认造成的布局闪动；不改变权威未读或离底提示。各阶段范围、验证和人工结果以各自 dated task 与 STATUS 为准。

- 每个问题运行对应项目的聚焦确定性测试；涉及 XAML/Windows UI 时至少完成 App Debug build，再交给用户进行最短真实窗口验证。
- 搜索、桌面体验和性能三个检查点各运行一次 Fast；若实际切片很小，可在 dated task 中说明复用相邻检查点，但不能用旧提交证据冒充当前树结果。
- 协议/session 写入结果确认完成后，进行一次独立只读复核，重点检查零重试、单次 readback、身份 generation 和错误脱敏。
- V2 全部已确认问题收口后，在最终候选精确 HEAD 运行一次 MAUI-only Full。Full 只运行 Release build/tests、Windows publish/ZIP 和安全检查，不重复 Fast 或历史 Web 门禁。失败必须保留真实失败项，不得通过降低标准规避。
- 不运行 Live，不发起真实群改名、公告、置顶、静音、邀请或成员变更，不执行部署、tag、签名、安装器或干净 VM；这些动作都需要以后单独授权。
- 提交/推送仍是用户确认后的最小 Git 事务：只暂存同一个已确认问题的代码、测试、工作日志和对应文档，永远排除 `.verify/` 与无关用户改动。

## 9. V2 完成条件

- 六个部分按顺序完成，所有行为与本计划一致，且没有通过兼容旧产品入口扩大范围。
- 搜索不存在同 ID 重复，左右搜索互不取消；消息匹配有明确视觉与语义标识。
- 四类群资料写入统一返回三态权威结果，模糊写入零重试且最多一次 readback。
- 新建群聊能使用完整可见成员目录；成员资料缓存有 TTL、失效、并发上限和失败回退。
- Windows 会话列表、弹层焦点、Narrator、字号/DPI 和底部新消息数量均通过用户 Visual Studio 人工确认。
- 解析缓存和会话行复用通过确定性回归，且未改变消息窗口、SQLite、未读或滚动状态机。
- 最终 Fast/Full 结果、独立复核和所有未验证外部门禁已写入 STATUS；没有运行或声称通过 Live、真实 Realm 写入、签名、安装器或干净 VM。

## 10. 明确不做

- `@` 候选、Realm 自定义表情、标为未读、presence、typing、应用退出后的后台 push、多账号、断点续传上传。
- Web 对齐或 Web 新功能；公开频道、旧多话题私有频道、命名话题和多人私信入口。
- Core reducer 重写、大型 `ShellViewModel` 拆分、SQLite/消息窗口/未读/滚动架构改造。
- Live、真实 Realm 写入、部署、公开发布、tag、签名、安装器和干净 VM 验收。

## 11. 假设

- Stage 30 `57c8145` 是 V2 的功能基线；后续首版发布提交属于必须保留的 `main` 历史，V2 实施从当时最新 `main` 继续。
- Windows 11 x64、MAUI-only 和单账号是本轮产品边界。
- 用户的 Visual Studio 真实窗口结果是 UI/交互验收依据；Agent 的构建与测试不能替代人工视觉结论。
- Zulip 12.1 及现有 Realm 权限模型继续作为协议和权威状态依据。
